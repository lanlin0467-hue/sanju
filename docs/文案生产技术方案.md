# 文案生产工具 技术方案(草稿 v0.2)

> 对应需求文档:`docs/文案生产需求文档.md`(v1.0)
> 已选定:**方案一**。方案二留作以后升级,这一版不实现。
> 本文用大白话写,面向第一次接触这类东西的人。

## 0. 先用一个比方说清楚这个工具在干什么

把它想成一家**代写小店**:

- **网页**是前台,客人在这里递上照片、描述和心情。
- **后台服务**是后厨的传菜窗口(行话叫"后端")。前台的单子先到这里,再由它去找写手。
- **大模型**是签约写手,看得懂图,也会模仿鲁迅、朱生豪、江南的腔调。
- **API 密钥**是小店挂在写手那里的记账卡,写手每写一次就刷一次。

记账卡不能放在前台,放在网页里谁都能抄走去刷。所以哪怕功能很简单,也必须有后厨窗口,这一点两个方案都一样。

## 方案一:一个全能写手,一次交三句(已选定)

### 技术选型

- **Next.js(TypeScript)**:前台页面和后厨窗口放在同一个项目、同一种语言里。以后自己改,只面对一个文件夹,不用在两套东西之间对来对去。
- **一个能看图的大模型 API**:看图和写句子都交给它。
- **浏览器自带的图片压缩**:手机原图动辄几 MB,先压小再发,不需要额外装库。
- **不用数据库**:需求里不存图片、不做账号和历史,没有需要存的东西。画面理解也只记在这张网页上。

### 数据流转

1. 用户选图或写描述,再写心情,点"生成"。
2. 网页先把照片压小,再把"图片 + 描述 + 心情"交给后厨。没有传图、只有文字描述时,这一步不带图片。
3. 后厨把这些连同一份"写作说明书"(行话叫提示词)一起交给写手。说明书要求两件事:先用几十个字写清看到的画面(谁、在哪、光线、在做什么、显眼的物件),再写三句,各 20 字左右,分别是鲁迅腔、朱生豪腔、江南腔。
4. 写手一次交回一段"画面理解"和三句。后厨先检查三句的字数,不合格就让写手重写一次,再把结果交给网页。图片到此为止,后厨不保存。
5. 网页记下画面理解,并显示出来,例如"我看到的是:黄昏的海边,一个人的背影"。下面是三句,每句旁边有"复制"和"换这句"。这段话用户可以直接改。
6. 点"换这句":单子里只有文字,也就是"画面理解 + 用户自己写的描述 + 心情",并注明"只重写某一种,别和之前的重复"。换出来的句子按这段文字来写,所以画面理解要写具体;写得太笼统,换句会丢细节。
7. 用户改完画面理解再点"生成",按改正后的文字重写三句,这一步同样不带图片。换句次数重新从 3 次算起。用户换了照片,或改了自己的描述、心情,旧的画面理解作废,重新走第 2 步。

没有传图时,画面理解就用用户自己写的描述,写手不必再转述一遍。

### 数据结构草图

```
网页发给后厨的"单子":
{
  图片:        压缩后的图片(第一次生成,或用户换了照片时才有),
  画面描述:    用户写的文字(可选),
  心情:        用户写的文字(必填),
  画面理解:    空,或网页上已有的那段话(换句,或按改正后的理解重写时带上),
  只换哪一种:  空 / 鲁迅 / 莎士比亚 / 江南   // 空 = 三种都写
  之前的句子:  []                            // 避免换句时重复
}

后厨的回复:
{
  画面理解: "黄昏的海边,一个人的背影,路灯刚亮",
  鲁迅: "…",
  莎士比亚: "…",
  江南: "…"
}
// 换句时,画面理解原样带回,三句里只有被换的那一项是新的

网页自己记着的状态:
{ 图片, 画面描述, 心情, 画面理解, 三句话, 剩余换句次数: 3 }
```

"画面"是图片和描述至少有一个,"心情"必填。画面理解只活在这张网页上,刷新就没了,后厨不保存。第一次的三句是看着原图写的;换句,以及按改正后的理解重写,都按画面理解这段文字来写。

### 优缺点和取舍

- **优点**:只有一份说明书要调,能最快验证"三种文风写得好不好"。这是整个产品最大的风险,架构反而是次要的。图片只在第一次生成(或用户换了照片)时传一次;换句只发文字,更快也更省。画面理解摆在句子上面,看错了用户改完就能重写。
- **还要接受的一点**:看图和写句子是同一个写手,两件事交给同一个模型。换出来的句子依据的是画面理解,所以这段话必须写具体。如果以后试下来这个写手文风不行、看图却很准,再升级到方案二。后厨已经按"换句只发文字"来写,改动不大。

## 方案二:先请"看图员"说成一段话,再请"写手"只看文字写(这一版不做)

和方案一的差别只剩一件事:看图和写作分成两次,可以各挑一个模型。换句只发文字、把画面理解给用户改,方案一已经做了。

### 技术选型

同样是 Next.js,但调用两次模型:

- 第一次用看图模型,把照片变成一段文字,比如"黄昏的海边,一个人的背影"。
- 第二次用中文写作最好的模型,拿这段文字加心情来写三句。

两位可以分别挑最合适的模型。

### 数据流转

上传、压缩、看图员、得到一段画面说明,网页把这段文字记下来,写手只拿文字写三句。之后"换这句"只发文字,图片早就丢掉了。用户直接写描述、没有传图时,跳过看图员,这时和方案一差不多。

### 数据结构草图

```
网页自己记着的状态:
{ 画面说明(文字), 心情, 三句话, 剩余换句次数: 3 }
```

### 优缺点和取舍

- **优点**:看图和写作可以各用最合适的模型。
- **缺点**
  - 第一次生成要等两轮,更慢一点。三句从一开始就按转述来写,原图里的细节会先丢一层。
  - 要维护两份说明书。

## 建议

已选定方案一,按上面的数据流转实现。后厨窗口写得独立一点,方便以后升级到方案二。

**选哪家模型**(任务 3 已定):

- **服务商**:OpenRouter。接口兼容 OpenAI 格式,地址 `https://openrouter.ai/api/v1`。
- **模型**:`qwen/qwen3.7-flash`(能看图、适合起步;以后只改后厨那一个文件就能换模型)。
- **密钥**:开发用的是别人账号下的一把 Key(不是你自己的号)。放在本地 `.env.local` 的 `MODEL_API_KEY`,不进代码、不进 git。任务 4 再接到项目里。
- **消费上限**:OpenRouter 后台你进不去,请账号主人设 Credits / Limits;项目侧另有每日最多 4 次写手调用(见任务清单)。长期使用应换成自己的号。
- **访问注意**:用户主要在中国大陆,OpenRouter 有时连不上。本机开发若失败,先检查网络;公开上线前再评估要不要换国内服务商。

## 以后自己改代码,特别容易踩的坑

1. **写作说明书是产品的灵魂。** 它藏在代码里,改一个字,三种文风可能全变味。建议单独放一个文件,改之前备份,再留一份"满意样例"做对照。目前三种风格都没有样例,建议各收集五句满意的,写进说明书当范例。同时要写明"模仿腔调,不要照抄原著原句"。说明书里还要写明画面理解必须具体:谁、在哪、光线、在做什么、显眼的物件。写得太笼统,换句就会丢细节。
2. **字数检查千万别删。** 大模型其实数不准字数,它是按"词块"在处理,写的"20 字"常常差很多。所以后厨必须用程序自己数一遍。"20 字左右"到底是 16 到 24 还是别的范围,需要拍板。字数只查三句文案,不查画面理解。
3. **API 密钥不要写进代码文件,也不要上传到 GitHub。** 放进"环境变量",也就是一个单独的、不上传的保密本子。泄露了别人会刷爆你的账,务必在服务商那里设好每月消费上限。
4. **"只能换三次"现在只在网页里数,刷新页面就能绕过。** 朋友间用没问题,公开上线后一定有人去刷。后厨也要按访问者限流,并设每日预算。以后改代码时别以为网页里那个"剩余次数"就是真的限制。
5. **"不留存图片"要靠自己守住。** 后厨里随手加一句"把收到的内容打印出来调试",图片和画面理解就留进日志了。两者都只应活在当次请求和网页上。图片也会经过模型服务商,他们有自己的数据保留规则,上线前要查清楚,否则隐私提示就成了空话。
6. **手机图片很麻烦。** iPhone 的照片格式(HEIC)、照片自动旋转的方向信息、太大的文件,都容易出问题。压缩那段代码每次改完都要用真手机测。
7. **复制按钮要在微信里试。** 核心用户是发朋友圈的人,会在微信内置浏览器里打开。那里的"复制"表现有时和普通浏览器不一样,每次改这块都要在微信里点一下。
8. **没有数据库就没有"历史"。** 将来想加历史记录或账号,就不是小改动了。这是主动做的取舍,已经在需求文档的"先不做"里。
